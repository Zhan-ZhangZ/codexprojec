# 1. ⚙️ 新技能完整集成要求 (Full Codebase Integration)

* **遵守 Git 分支规范**：现在只有一个主分支 `main`。每次集成新技能时，**必须**从主分支（`main`）创建新的功能分支进行处理，严禁直接在主分支上开发，完成后没问题再合并。
* **不要只写说明文档**：集成新技能时，严禁仅创建 `SKILL.md`。必须将原项目的**完整源码仓库**克隆到对应分类的技能文件夹中。
* **冲突清理**：克隆完成后，必须立即彻底删除该技能文件夹内自带的 `.git`、`.github` 目录以及所有的 `.gitignore` 文件，防止主仓库 Git 发生嵌套冲突和严重的漏追踪（如核心源码、SKILL.md被错误忽略）。
* **无价值文件 AI 审查（瘦身红线，必须由 AI 判断，严禁机械黑白名单脚本代替）**：「完整源码仓库」指保留技能**运行所需**的源码与文档，**不含**上游的开发过程产物。审查方法分两步：
  1. **先读懂项目结构再动手**：集成前必须先看清上游仓库的整体结构，分清哪些是**技能驱动的东西**（SKILL 入口、工作流文档、运行脚本及其依赖数据——Agent 执行技能时要读要跑的），哪些是**开发者多余上传仓库的东西**（CI 配置、测试套件、评测产物、历史报告、展示样例、治理文件——只服务于上游开发流程）。分不清这一层，后面删什么都靠猜。
  2. **以文件夹为单位、一眼扫描判断，不逐文件细究**：看文件夹名和里面内容的形态即可定性（例如「这部分是展示样例」，扫一眼文件夹就知道与技能功能无关，整目录剔除）。只有当文件夹内混杂运行链路文件时（如 `scripts/` 散文件里运行脚本与 CI 验证器混居），才退到「保留集文档实际引用了哪些」的链条口径逐个圈定。
  
  判断标准只有一条——「该内容缺失时，技能还能否被 Agent 完整调用执行？」。判断为无价值的内容**必须删除**，并在集成提交信息中记录判断结论（删了什么、为何判断无价值）。审查时重点覆盖以下**典型嫌疑对象**（仅是 AI 审查的切入点，不是免检清单，最终去留必须逐项给出判断）：
  * 上游评测与测试产物：`evals/`、`tests/`、`fixtures/`、评测 `runs/` 历史输出等——历史事故根源：academic-research-skills-codex 的深层 evals 目录直接导致 Windows 客户解压失败；
  * 依赖与构建产物：`node_modules/`、`__pycache__/`、`.venv/`、`dist/`、`build/`、`coverage/` 等；
  * IDE/环境配置：`.idea/`、`.vscode/`、`.cursor/` 等；
  * 与技能运行无关的大体积媒体、数据集、演示样例；
  * 包内部自带的多份相同子树（如 `plugins/` 包装副本与 `skills/` 正文重复——历史事故：1738 个文件被重复打包两份），只保留一份。
  注意：**疑似无价值 ≠ 直接删除**。例如名称含 `test` 的目录里可能藏着技能运行必需的词典/模板，必须打开确认内容性质后再决定；同理，**有价值的也不许漏删审查**——审查是全量的，不是只扫嫌疑名单。
* **重复集成检查**：集成前必须确认**同名技能文件夹**未存在于其它类目（跨类目重复集成）；同时警惕上游包内部自带的多份相同子树（如 `plugins/` 包装副本与 `skills/` 正文重复），只保留一份。
* **路径长度硬性检查（Windows 兼容红线）**：剔除与清理完成后、登记 `skills_manifest.json` 之前，**必须**运行客观项准入检查脚本并看到「✅」：
  ```bash
  python3 scripts/integration_check.py "<技能文件夹路径>"
  ```
  检查口径：从库根 `codex-skills/` 到文件的相对路径**字符数**（Windows MAX_PATH=260 按 UTF-16 字符计，一个汉字算 1 个）：
  * **> 200 字符 = 警告**（客户机用户名稍长、OneDrive 重定向目录即会超限）；
  * **> 219 字符 = 拒绝集成**（按客户典型安装前缀 `C:\Users\<user>\.codex\skills\codex-skills\` 约 41 字符 + 219 = 260 推算）。
  超限时必须缩短技能内部目录嵌套或删除深层无价值文件后**复检通过**，严禁带病登记清单。该脚本同时会校验 `SKILL.md` 存在性与跨类目重名；**无价值文件的判断与删除由 AI 按上一条规则完成，脚本不做价值判断**。
* **引用完整性闭包复检（删除后的第二道红线）**：删除审查会连带删掉「被保留文档引用着的文件」，造成大量断链——历史事故：2026-09 子代理集成 academic-research-skills-codex 时一次性产生 **55 处文档互链死链**（README 指向 CHANGELOG、安全报告、设计文档等被误删）。因此清理完成后，**必须**追加死链扫描并看到结论：
  ```bash
  python3 scripts/integration_check.py "<技能文件夹路径>" --refs
  ```
  对扫描出的每一条死链，按目标性质三选一处置（**由 AI 对照上游原树逐条判断**，脚本只罗列事实）：
  * **本次集成删掉了被引用的运行链路文件** → 必须归零：要么补回该文档，要么改写引用。补回后**重跑扫描迭代**，直到不再出现新断链（补回的文档自身也可能引用已删文件）。冗余翻译变体（如 `README.ja-JP.md`）被删时，改写语言切换栏指向保留的那个变体，而不是补回所有语言；
  * **本次集成删掉的开发基建（CI/测试/评测/示例）被保留文档提及** → 属叙述性提及，保留原貌不追链（历史文档描述「测试怎么跑」本就不构成技能运行链路），但必须在集成提交信息中**披露数量**；
  * **上游原树本来就缺** → 保留原貌，提交信息中披露数量。
  另注意：**目录布局扁平化（如剥掉上游 `skills/<name>/` 一层前缀）必须全局改写保留文档里的旧前缀引用**，否则会产生整批路径死链（同一历史事故中 17 处旧前缀引用漏改）。
* **上游仓库登记（索引表维护红线）**：集成时**必须**同步完成两件事：① 在技能 `SKILL.md` frontmatter 的 `metadata` 中写入 `upstream: "<仓库地址>"`（如 `github.com/xxx/yyy`）；② 在仓库根的 `技能仓库索引.md` 对应类目下增补一行（技能 / 仓库 / 置信 ✅ / 证据）。历史教训：早期集成未记录来源，导致 53 个技能的上游仓库无法追溯，版本更新无从下手。上游为自研技能时标注「本仓库自研」。
* **推送与 MCP 验证**：完成集成并合并回 `main` 后，必须推送到远程仓库（`git push origin main`），并执行 MCP 端到端验证（搜索召回、主文档读取、关键文件加载），确保下游各客户端可正常消费。详细规范见 `references/06_e2e_verification.md`。
