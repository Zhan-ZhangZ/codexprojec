# 5. 📦 备份、打包与交付流程 (Backup & Packaging Workflow)

> **注意**：打包流程并不是每次集成技能时都需要执行的。**不要默认在集成后进行打包**，打包操作需要用户主动触发时才执行。如果用户要求打包，请遵循以下流程：

必须严格遵循“先备份旧包，再打包新包，双包输出”的流程：

**【集成前】**
1. **前置备份与轮转清理**：在集成新技能前，必须先将当前项目根目录下的 `codex-skills*.7z` 或 `.zip` 移动并重命名（附带时间戳）到 `备份包文件夹` 目录中。同时，检查并清理 `备份包文件夹`，**只保留最近的两个版本备份包**，删除更早的历史包。
2. **路径长度预审**：运行 `python3 scripts/check_integration_paths.py` 扫描整个 `codex-skills/` 树，模拟 Windows 客户提取后的完整路径。任何长度 > 200 字符（包内相对）的文件**必须**先在集成阶段清理掉（参见 `01_integration.md` 第 1.1 节），**禁止**通过修改 `repack_7z.py` 加 `-xr!` 规则来掩盖问题。

**【集成后】**
3. **全量打包**：运行 `python3 scripts/repack_7z.py -v <版本号>` 重建最新的 7z 全量包。该脚本会**自动**先调用 `check_integration_paths.py`，如有违例立即报错退出，禁止产出坏包。为了配合云端原生版本管理，全量包在本地的输出名称将保持为当日日期的 `codex-skills-日期.7z`（历史归档仍会在本地备份目录中妥善保留），例：codex-skills-7月9日.7z。
4. **增量打包**：运行增量打包脚本（如 `python3 scripts/repack_incremental_7z.py -b <baseline_commit> -v <版本号>`），生成的增量包会带有日期时间和版本号后缀，并输出至 `增量包文件夹` 中。（注：`增量包文件夹` 内也只保留最近 2 份增量包）增量包同样受 `check_integration_paths.py` 卡口保护。
5. **结构与逻辑校验**：脚本会自动调用 7z 自检命令进行结构损坏校验。同时，**必须执行内容审查（如检查 `skills_manifest.json` 等关键文件是否存在且内容完好），确保打包逻辑正确，包内结构无误**。
